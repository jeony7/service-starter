# Service Starter

Kotlin/Spring 서버와 React 화면을 함께 개발하는 스타터입니다. 요구사항별로 작은 사용자 흐름을 구현하고, 필요한 업무 계산을 설계·연결하며 인수 기준과 검증·평가 근거를 남깁니다.

## 시작

```bash
git clone https://github.com/jeony7/service-starter.git
cd service-starter
```

1. [AGENTS.md](AGENTS.md)와 요구사항 정리 스킬을 읽도록 요청하고, 실행 환경·산출물 제약을 먼저 확인합니다.
2. 기능과 공통 제약을 정리하면서 [앱 실행 안내](app/README.md)에 따라 화면·API·DB 연결을 확인합니다. 서로 독립적인 정리와 환경 준비는 병행할 수 있습니다.
3. Docker를 사용하는 환경이면 포함된 Dockerfile을 `docker build`·`docker run`으로 빌드·기동하고 데이터 볼륨을 초기에 확인합니다. 지정 실행 방식이 있으면 우선하고, 도구가 없어 실행하지 못한 범위는 기록합니다.
4. [요구사항 문서](docs/REQUIREMENTS.md)에서 다음 작은 UC와 완료 기준을 정합니다. 데이터·상태 계약을 바꾸는 미정 사항은 먼저 확인하고 화면·API·저장·재조회가 이어지는 사용자 흐름을 만듭니다.
5. 복잡한 업무 규칙·계산·탐색이 필요한 기능에서는 [업무 로직 설계 스킬](.agents/skills/design-business-logic/SKILL.md)을 적용합니다. 작은 사례로 문제를 이해하고 풀이·검증 계획을 정한 뒤, 실제 업무 코드를 UC에 연결합니다. 단순 조회·저장에는 이 절차를 추가하지 않습니다.
6. UC별 실제 동작을 검증하고 다음 범위를 진행합니다. 최적화가 필요하면 조건을 만족하는 기준 구현과 품질·실행시간을 비교합니다. 전체 부가 기능을 끝내거나 복잡한 알고리즘을 완성할 때까지 모든 연결을 미루지 않습니다.

```text
요구사항·데이터·실행 환경 확인
              |
작은 UC 선택 / 입력·결과·AC 정의
              |
필요한 업무 판단 이해·설계 + 화면·API·저장 연결
              |
실제 업무 코드 연결 / AC 검증
              |
필요한 품질·실행시간 개선 → 같은 조건으로 비교
              |
다음 UC → 전체 흐름·실행 방식 확인
```

업무 판단은 `작은 사례 → 풀이 선택 → 검증 계획 → 구현 → 실제 평가` 순서로 좁힙니다. 선택한 방법에 따라 규칙 계산·탐색·DP·반복 개선 등의 절차가 달라집니다. 사용자에게 보여줄 때는 현재 기능의 ASCII 흐름, 작은 입력의 중간 판단과 결과, 다음 결정부터 설명합니다.

```text
AGENTS.md와 .agents/skills/define-requirements/SKILL.md를 읽고
제공한 자료에서 기능 요구사항과 공통 제약을 정리해줘.
실행 환경과 산출물 제약을 먼저 확인하고,
app/README.md를 따라 기본 템플릿의 실행 환경도 함께 준비해줘.
화면·API·H2 연결을 확인하고, Docker를 사용할 수 있으면
포함된 Dockerfile로 docker build·docker run과 볼륨 데이터 보존을 확인해줘.
실행하지 못한 항목은 구분해서 기록해줘.
사용자 흐름을 ASCII로 보여주고, 다음 구현 범위를 제안해줘.
핵심 업무 판단과 계약을 바꾸는 미정 사항을 식별하고,
필요한 판단은 작은 사례로 설명해줘.
업무 기능은 구현 범위를 정한 뒤 진행해줘.
```

```text
AGENTS.md와 .agents/skills/implement-usecase/SKILL.md를 읽고
합의한 기능의 첫 UC를 구현해줘.
화면·API·저장·재조회를 연결하고, 복잡한 업무 판단이 있으면
design-business-logic 스킬로 풀이와 검증 계획을 정해 실제 코드에 반영해줘.
인수 기준별 검증 수단과 실제 실행 근거·결과를 갱신해줘.
```

업무 판단을 먼저 이해하거나 대안을 비교할 때는 다음처럼 요청할 수 있습니다. 이 요청은 설계 범위이며, 구현까지 요청한 경우에는 같은 승인을 반복하지 않고 합의한 범위를 진행합니다.

```text
현재 기능과 .agents/skills/design-business-logic/SKILL.md를 읽고
입력·출력·결정할 것·필수 조건·개선 목표를 정리해줘.
작은 입력을 직접 풀어 중간 상태와 기대 결과를 보여줘.
입력 규모에 맞는 풀이 후보와 보장 범위·계산 비용을 비교하고,
한 방법의 후보 생성·선택·종료 규칙을 구체적으로 설명해줘.
구현 전에 AC의 검증 방법과 필요한 비교 지표를 정리해줘.
기존 문서의 해당 기능과 설계 결정에 연결해줘.
```

```text
AGENTS.md와 .agents/skills/verify-delivery/SKILL.md를 읽고
필수 요구사항의 현재 결과와 통합 실행을 확인해줘.
지표가 필요한 기능은 실제 측정 근거까지 확인해줘.
```

## 구조

```text
AGENTS.md             작업 기준과 필요한 지침으로의 연결
.agents/skills/       요구사항 / 구현 / 필요한 업무 로직 설계 / 전체 검증
docs/
  REQUIREMENTS.md     기능·제약·UC·필요한 업무 판단·인수·검증·평가
  DECISIONS.md        중요한 선택과 근거
  STACK.md            코드 구조와 기술 규칙
  COLLABORATION.md    필요할 때만 읽는 위임 지침
app/
  backend/           Kotlin / Spring / JPA / H2
  frontend/          React / TypeScript / Vite / Tailwind
  README.md          설치·빌드·실행·사용·DB 조회
  Dockerfile
```

`app/`은 독립적으로 빌드·실행할 수 있습니다. 업무 요구사항과 데이터는 프로젝트에서 추가합니다. 현재 스택과 실제 환경이 충돌할 때만 필요한 부분을 조정합니다. 검사 도구는 설정되어 있지만 lint·포맷은 명시적으로 요청할 때만 실행합니다.
