# 요구사항

## 서비스 요약

- 목표:
- 사용자:
- 입력·출력:
- 핵심 업무 판단: 프로그램이 계산하거나 결정할 내용. 단순 조회·저장만 있으면 해당 없음
- 실행 환경·산출물:
- 가정·미정 사항과 출처:

## 전체 사용자 흐름

ASCII 코드 블록으로 주요 행동과 상태 변화, 중요한 실패 분기를 표시한다.

## 기능 목록

| ID | 기능과 사용자 목표 | 우선순위 | 상태 | 다음 UC |
|---|---|---|---|---|

상태는 미정·구현 전·구현 중·검증 중·완료로 구분한다. 필수 UC나 적용 제약이 미확인인 기능은 전체 완료로 표시하지 않는다.

## 공통 제약

| ID | 규칙·단위·경계 | 출처·확정 여부 | 적용 기능 |
|---|---|---|---|

같은 규칙의 원문은 이곳에만 둔다. 기능에서 C ID로 참조하고 실제 적용 경로의 검증은 해당 기능 아래 기록한다. 아직 요구되지 않은 기능을 적용 경로로 추가하지 않는다.

## 기능 상세 양식

아래 양식을 필요한 기능마다 복사한다. 큰 기능은 작은 사용자 목표로 나누고 다음 구현 UC부터 상세화한다.

### F-ID — 기능명

- 목적·사용자:
- 출처·확정/가정/미정:
- 범위·범위 밖:
- 적용 제약: C ID 참조
- 현재 상태·다음 작업:

#### 기능 흐름 — ASCII

각 기능 상세의 앞부분에 사용자 행동, 관련 UC의 연결·분기, 성공 결과와 상태 변화, 중요한 실패 결과를 그림으로 표시한다. 필요한 조건·분기에는 C/AC ID를 붙여 아래 정의와 연결한다. 아래 형태를 실제 기능에 맞게 바꾸며, 존재하지 않는 단계나 UC 간 연결을 만들지 않는다.

```text
[사용자 행동]
      |
      v
[UC-ID: 처리] -- 실패 --> [실패 결과]
      |
      v
[성공 결과 / 상태]
```

그림이 복잡해지면 기능 그림은 개요로 유지하고 해당 UC에 상세 흐름을 나눈다. 단순한 기능은 하나의 그림을 기능과 UC 설명에 함께 사용한다.

#### 업무 판단 — 필요한 기능에만 추가

복잡한 규칙·계산·탐색이 있을 때만 작성한다. 다음 구현 범위부터 구체화하고 동일 판단을 쓰는 UC는 이 절을 참조한다. 작은 사례의 기대 결과는 구현 전에 정하며, 실행 근거는 아래 AC 검증 기록에 연결한다.

- 입력·출력·프로그램이 결정할 것:
- 고정된 사실·정책값·미정 사항: 출처와 적용 C 참조
- 작은 사례: 정상·경계·불가능 사례 중 관련 입력과 기대 결과·판단 이유
- 선택한 풀이·보장 범위: 관련 D-ID 참조
- 구현·연결 상태: 임시 연결 / 기준 구현 / 개선 구현과 현재 코드·API·저장 경로
- 검증 계획: 관련 AC, 적절한 정답·불변 조건·비교 근거
- 품질·실행시간 평가: 필요한 경우 아래 지표 참조

필수 조건과 품질 목표를 구분한다. 아직 조건을 만족하는 결과를 만들지 못한 상태, 탐색 중단, 불가능이 증명된 상태를 같은 실패로 기록하지 않는다. 적용할 구분은 실제로 선택한 풀이에 맞춘다.

#### UC-ID — 사용자 행동

- 입력·전제:
- 성공 결과·실패 결과:
- 상세 흐름: 필요한 경우 ASCII. 기능 그림과 같으면 해당 그림을 참조

| AC ID | 구분: 기능/기술 | 입력·상황 | 기대 결과 | 적용 C |
|---|---|---|---|---|

AC에는 현재 기능의 위험과 관련된 기술적 조건도 작성한다. 여러 기능에 공통인 기술 제약은 C에 한 번 정의하고 참조한다. 모든 기능에 동시성·타임아웃 검사를 일괄 추가하지 않는다.

- 동시성: 무엇을 두고 경합하는지, 동시에 수행할 요청·트랜잭션 조건, 허용 성공/실패 결과, 최종 데이터 불변 조건을 명시한다.
- 타임아웃: DB 잠금 대기·외부 호출·요청 응답 중 발생 지점과 제한 시간의 근거, 오류 응답, 저장·롤백·후속 처리의 기대 상태를 명시한다. 클라이언트 응답 종료와 서버 처리 취소를 구분한다.
- 재시도·중복 처리 등이 관련되면 같은 요청을 다시 보냈을 때의 기대 상태를 정한다. 미정인 수치와 정책은 사용자와 확인하기 전까지 미정 또는 제안으로 표시한다.

기술 AC의 필수 통과 조건과 선택적인 성능·최적화 평가 지표는 구분한다.

#### 인수 체크리스트와 검증 기록

AC별로 체크리스트를 두고 아래 기록을 연결한다. 기대 결과는 실행 전에, 관찰 결과는 실행 후 작성한다. 여러 수단을 사용했으면 각 수단의 기록을 구분하고, 확인한 범위를 종합해 AC를 판정한다. 작성된 테스트가 미실행이면 체크하지 않는다.

```text
[ ] AC-ID — 완료 조건
검증 수단: 자동 테스트 코드 / 임시 검증 스크립트 / 수동 확인
검증 범위: 단위 / DB 통합 / API / 화면 등
코드 근거: 파일·테스트명 또는 스크립트. 없으면 없음
실행 여부: 실행 / 작성만 함·미실행 / 차단
실행 근거: 명령·결과 자료 또는 수동 재현 절차·확인 자료
대상·환경: 결과에 영향을 주는 코드 버전·프로필·DB·입력
실행 세부: 아래 수단별 항목 중 해당 내용
관찰 결과:
판정: 통과 / 실패 / 미실행 / 차단
미확인 범위:
```

수단 이름만 적지 않고 실제 사용한 내용을 아래 기준으로 기록한다. 사용하지 않은 수단의 양식은 만들지 않는다. 관련 요청·쿼리·응답은 짧은 코드 블록으로 보여주고, 긴 실행 로그는 파일 링크로 연결한다. 비밀 값과 개인정보는 가리되 재현에 필요한 입력의 의미는 유지한다.

| 검증 수단 | 남길 실행 세부 |
|---|---|
| 자동 테스트 코드 | 파일·클래스·테스트명, 실행 명령, 준비 데이터·입력, 핵심 assertion의 기대값과 관찰 결과, 실행 건수·실패·오류 및 보고서 근거 |
| 임시 스크립트 | 스크립트 파일 또는 코드, 실행 명령·인자·입력, 출력, 자동 assertion인지 수동 대조인지 구분 |
| API 직접 확인 | HTTP 메서드·경로·쿼리 파라미터, 인증 역할·필요 헤더, 요청 본문, 실제 응답 상태·본문, 필요한 저장 상태 변화와 재현 명령 |
| SQL·DB 확인 | 실제 연결 DB·스키마, 실행 SQL과 바인딩 값, 준비 데이터, 트랜잭션·자동 커밋 조건, 전후 조회 결과·행 수, 변경 시 커밋/롤백·정리 여부 |
| 화면 수동 확인 | 역할·시작 경로·초기 상태, 입력·클릭 순서, 표시된 결과·오류, 확인 자료와 필요한 서버/DB 연계 결과 |

동시성 검증은 별도 연결·트랜잭션이 실제로 경합하도록 실행한 방법, 동시 실행 수·시작 동기화, 각 요청 결과와 최종 저장 상태를 남긴다. 순차 실행이나 단일 Mock 결과를 실제 경합 확인으로 기록하지 않는다. 타임아웃 검증은 지연·잠금 등 발생 조건을 만든 방법, 적용 설정·측정된 경과 시간, 응답·예외와 관련 저장/후속 상태를 남긴다. 추가 SQL 조회로 검증하면 그 쿼리와 결과도 같은 AC에 연결한다.

#### 평가 지표 — 필요한 기능에만 추가

성능·비용·최적화 평가가 불필요하면 이 절을 생성하지 않는다. 필요한 경우 지표별로 아래 항목을 작성한다.

```text
지표·선정 이유:
계산식·단위·판정 또는 비교 기준:
입력 근거: 데이터·버전·필터·분모
비교 대상과 공통 조건:
측정 수단: 자동 테스트 / 평가 스크립트 / 수동 집계 등
실제 측정 대상: 예시 구현 / 실제 앱 결과 / API 등
실행 근거: 코드·명령·출력 자료 / 미실행이면 미실행
측정값·해석·확인 범위·한계:
```

필수 조건을 통과한 결과를 대상으로 품질을 비교한다. 난수·반복 횟수·실행 환경은 결과에 영향을 줄 때 기록한다. 기능 사이의 통합 결과는 관련 F/UC/AC에 연결하고 동일한 로그를 여러 곳에 복사하지 않는다.
