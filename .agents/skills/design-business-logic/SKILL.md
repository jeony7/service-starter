# 업무 로직 설계

현재 F/UC, 적용 C/AC, 입력 데이터의 관련 부분과 기존 구현만 읽는다. 규칙·작은 사례는 [REQUIREMENTS](../../../docs/REQUIREMENTS.md)의 해당 기능에, 풀이 선택은 [DECISIONS](../../../docs/DECISIONS.md)에 연결한다. 별도 알고리즘 문서를 기본으로 생성하지 않는다.

## 이해와 선택

1. 입력·출력, 고정된 사실·정책값, 프로그램이 결정할 것, 필수 조건과 개선 목표를 구분한다. 데이터 규모·시간·단위·날짜 경계·실패 의미 등 풀이를 바꾸는 미정 사항부터 확인한다. 답에 따라 계약이 달라지는 질문은 해결하고, 독립적인 환경 준비·기본 흐름 작업은 계속한다.
2. 작은 정상 사례와 경계·불가능 사례의 기대 결과를 구현 전에 정한다. ASCII와 짧은 표로 입력 → 중간 판단 → 결과를 설명한다. 가능한 해가 여러 개면 아래 목표 정의 기준에 따라 어떤 결과를 더 좋다고 보는지 정한다. 실현 가능성 판정과 품질 비교를 구분한다.
3. 규칙 계산·그리디·탐색·DP·최적화 도구 등 문제에 맞는 풀이를 선택한다. 선택이 자명하면 길게 비교하지 않고, 대안이 결과를 바꾸면 기준 구현과 유력 대안을 비교한다. 입력 규모, 구현 비용, 최적성 보장 범위와 실행 비용을 설명한다. 모든 문제를 초기해와 반복 개선으로 해석하지 않는다.
4. 선택한 풀이의 상태·자료구조, 후보 생성 범위, 조건 검사, 선택·재배정 규칙과 종료 결과를 구체화한다. 탐색이면 불가능해서 제거하는 가지와 계산량을 줄이려고 제외하는 후보를 구분한다. 반복 개선이면 초기해, 한 번에 바꾸는 범위, 후보별 평가, 채택·동률·종료 기준을 정한다. 반복 수 × 후보 수 × 후보당 전체 계산을 포함해 비용을 본다. 전체 결과를 재평가하는지, 일부를 고정하는지도 명시한다.

## 목표 정의 — 최적화가 필요한 경우

- 풀이를 선택하기 전에 `결정변수와 허용값 → 선택 결과의 계산 → 필수 제약 → 목적함수`를 구분한다. 변수의 상관관계나 결과 계산식만으로 좋은 결과의 기준이 정해지지는 않는다. 조건을 만족하는 답 하나만 필요하면 목적함수를 추가하지 않는다.
- 요구사항의 출처를 근거로 `반드시 무엇을 지키면서, 무엇을 최대화/최소화하는가`를 먼저 문장으로 정한다. 이후 계산식·단위·최대/최소 방향·필요한 동률 기준으로 옮긴다. 비용·품질·시간 등의 트레이드오프에서 무엇이 필수 한도이고 무엇이 개선 목표인지 구분한다.
- 여러 목표를 하나의 가중합으로 만드는 것을 기본값으로 삼지 않는다. 필수 제약과 주목표로 표현할 수 있는지 먼저 본다. 우선순위·가중치·정규화가 필요하면 근거와 결과에 미치는 영향을 기록하고, 미정인 정책은 질문하거나 가정으로 표시한다. 필수 위반을 좋은 점수로 상쇄하지 않는다.
- 작은 결과 쌍에서 기대하는 선호 순서를 먼저 정하고 평가식이 이를 반영하는지 확인한다. 목표가 충돌하는 결과도 비교해 의도한 절충인지 설명한다. 손실·목적함수 후보는 각자의 원시 점수 크기가 아니라 공통 입력·필수 조건·실제 업무 지표로 비교한다. 점수의 배율만 줄인 것을 개선으로 판단하지 않는다.
- 결정변수가 이산·연속·혼합 중 무엇인지 확인한다. 기울기 기반 방법을 검토할 때만 연속성·미분 가능성과 기울기의 유용성을 확인한다. 평평한 구간의 기울기 0과 경계의 미분 불가능을 구분하고, 일부 수치 실험을 전체 매끄러움의 증명으로 취급하지 않는다. 모든 목적함수를 미분 가능한 손실로 바꾸려 하지 않는다.
- 근사 점수·샘플링·완화로 탐색했다면 최종 결과를 원래 조건과 실제 지표로 다시 평가하고 보장 범위를 밝힌다. 결과가 나쁘면 평가식의 선호가 잘못됐는지와 탐색이 좋은 결과를 찾지 못했는지를 나눠 확인한다. 정의와 작은 사례는 관련 F/C/AC에, 정책·풀이 선택의 근거는 D-ID에 연결한다.

## 검증 계획과 구현

5. 구현 전에 관련 AC의 입력·기대 결과·검증 수단을 정한다. 필수 조건을 독립적으로 검사할 방법과, 필요한 경우 기준 구현 대비 품질·실행시간 측정 방법을 정한다. 작은 완전탐색·수작업 정답·불변 조건·기존 도구 중 적절한 비교 근거를 사용한다. 알고리즘의 판단을 그대로 복제한 검사만으로 정확성을 주장하지 않는다.
6. 합의된 구현 범위에서는 선택한 기준 풀이를 작동하는 코드로 작성한다. 후보 생성·배정 변경·조건 검사·평가·종료 등 핵심을 이름만 있는 함수나 TODO로 남겨 완료 처리하지 않는다. 설명할 때는 실제 입력 하나의 중간 상태와 선택·제외 이유를 보여준다. 실험 코드와 실제 앱이 사용하는 코드를 구분한다.
7. DB·HTTP에 의존하지 않는 업무 계산은 Domain에 두고, Service에서 입력 확보·호출·필요한 저장·실패 처리를 연결한다. 단순한 규칙에 전략 인터페이스나 별도 엔진을 의무적으로 추가하지 않는다. 계산 결과가 해당 UC에 필요한 화면·API·저장·재조회 경로로 이어지는지 확인한다. 미구현 응답이나 규칙을 만족하지 못한 결과를 성공으로 확정하지 않는다.
8. 실제 실행으로 AC와 필요한 지표를 갱신한다. 선택적 최적화는 동작하는 기준 구현과 같은 조건으로 비교한다. 조건 위반을 비용 점수로 상쇄하지 않는다. 난수·반복 제한·시간 제한은 결과에 영향을 줄 때 기록한다. 탐색 실패·시간 초과를 불가능의 증명으로, 유효한 결과를 전역 최적해로 표현하지 않는다. 모델·후보·고정 범위 안에서의 보장인지 구분한다.

## 진행과 기록

- 흐름은 `이해 → 작은 사례 → 풀이 선택 → 검증 계획 → 구현 → 실제 평가 → 필요한 개선`이다. 이미 확인된 단계는 재사용하고 승인된 범위를 매 단계 재승인받지 않는다. 사용자가 이해·설계만 요청했다면 그 범위를 따른다.
- 처음에는 해당 기능의 입출력과 작은 사례, 다음 결정만 짧게 보여준다. 선택을 바꾸는 근거가 생겼을 때 설명을 보충한다. 새 풀이를 검토할 때도 관련 항목만 갱신한다.
- 코드·검증·서비스 연결이 어디까지 완료됐는지 구분한다. 구현하지 않은 분할·병합·재시도·동시성 처리 등을 구현된 동작처럼 설명하지 않는다. 실제로 사용한 AC 근거·평가 결과는 기존 기록을 참조하고 중복 복사하지 않는다.
