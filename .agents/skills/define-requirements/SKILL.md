# 요구사항 정리

[docs/REQUIREMENTS.md](../../../docs/REQUIREMENTS.md)를 기준으로 한다. 현재 자료와 관련 항목부터 읽고 이미 확인한 내용은 재사용한다.

1. 목표·사용자·입출력·필수 기능·공통 제약·개선 목표·실행 환경·산출물 형식을 구분한다. 각 항목에 출처를 연결하고, 명시된 사실·이해관계자 답변·가정·미정을 구분한다. 선호 사항을 명시적 근거 없이 필수 조건으로 확정하지 않는다.
2. 독립적으로 설명·변경·판정할 수 있는 기능에 F ID를 붙인다. 큰 기능은 묶음으로 두고 작은 사용자 목표로 나눈다. 여러 기능에 적용되는 제약은 C ID로 한 번 정의하고 적용 기능에서 참조한다.
3. 상단에 ASCII 사용자 흐름과 기능 목록을 작성한다. 각 기능 상세의 앞부분에도 사용자 행동·관련 UC의 연결과 분기·성공 결과·중요한 실패 결과를 짧은 ASCII 그림으로 표시한다. 필요한 분기는 C/AC ID에 연결하고, 복잡한 흐름만 해당 UC에서 상세화한다. 단순한 기능은 하나의 그림을 함께 사용한다. UC 개수나 문서 분리를 강제하지 않고, 제약 때문에 요구되지 않은 기능을 추가하지 않는다.
4. 다음 구현 범위의 UC부터 입력·성공 결과·정상/실패 흐름·범위 밖·인수 기준(AC)을 구체화한다. 기능 동작·적용 제약과 함께 관련된 동시성·타임아웃·중복 처리 등 기술적 조건을 반영한다. 경합 대상·허용 결과·최종 저장 상태, 타임아웃 지점·제한·실패 후 상태를 구체화한다. 근거 없는 수치나 불필요한 기술 조건을 일괄 추가하지 않는다.
5. AC별 적절한 검증 수단과 범위를 계획한다. 테스트 코드·API·화면·SQL 확인을 구분하고, REQUIREMENTS의 수단별 기록 기준에 맞춰 어떤 입력·요청·쿼리와 결과를 확인할지 정한다. 동시성은 실제 경합을, 타임아웃은 발생 조건과 이후 상태를 확인할 방법을 계획한다. 아직 실행하지 않은 결과는 미실행으로 둔다.
6. 성능·비용·최적화 품질이 중요한 경우에만 지표를 추가한다. 선정 이유·계산식/단위·판정/비교 기준·입력/분모·측정 수단을 정한다. 임의의 임계값을 요구사항으로 만들지 않는다.
7. 결과를 바꾸는 미정 사항을 사용자와 논의한다. 독립적으로 진행할 수 있는 정리는 계속한다. 다음에 구현할 작은 범위와 완료 기준을 보여준다. 요구사항 정리만 요청받았다면 구현하지 않는다.

변경 시 관련 F/C/UC/AC ID를 유지하고 영향받는 구현·검증·지표를 표시한다. 실제 구현에 맞추려고 인수 기준을 낮추지 않는다. 상세 로그와 대화 전체를 문서에 붙이지 않는다.
