# 기능 구현

현재 F/UC, 적용 C, AC, 관련 결정·계약과 담당 코드·테스트부터 읽는다. [기술 규칙](../../../docs/STACK.md)과 [실행 안내](../../../app/README.md)는 필요한 부분만 확인한다.

1. 현재 요청의 구현 범위와 완료 기준을 확인한다. 입력·상태·시간/단위·실패 의미 중 데이터 구조와 계약에 영향을 주는 미정 사항을 먼저 해결한다. 이미 승인된 연속 범위는 같은 승인을 다시 묻지 않고 수행한다.
2. API 입력/출력·오류·상태 의미와 저장 경계를 정한다. 기본 사용자 흐름을 먼저 연결하고 복잡한 계산은 필요할 때 좁혀 논의한다. 필수 제약은 임시 구현에서도 유지한다.
3. 직접 수행·일부 위임·여러 담당 분담은 작업량·독립성·조율 비용으로 판단한다. 위임할 때만 [협업 지침](../../../docs/COLLABORATION.md)을 읽는다. 프론트/서버 구분만으로 자동 위임하지 않는다.
4. 기능의 수용 기준과 위험에 맞춰 검증한다. 업무 판단은 단위 테스트, 저장·롤백은 DB 통합, 권한은 실제 API 경로, 화면은 브라우저 등 적절한 수단을 선택한다. 기술 AC가 있으면 별도 연결·트랜잭션의 실제 경합이나 의도한 타임아웃 조건을 만들고 요청별 결과와 최종 저장·후속 상태를 확인한다. 중요 규칙은 기대 결과를 구현과 독립적으로 정한다. 단순 DTO·문구를 검사 수 확보용으로 테스트하지 않는다.
5. 각 AC에 사용한 수단별로 REQUIREMENTS의 실행 세부를 기록한다. 자동 테스트는 파일·테스트명·입력·핵심 assertion·명령·결과를, API 직접 확인은 메서드·경로·요청·실제 응답을, SQL 확인은 DB·쿼리·바인딩 값·트랜잭션 조건·전후 조회 결과를 연결한다. 재현 가능한 근거·판정·미확인 범위를 남기고 비밀 값·개인정보는 가린다. 임시 스크립트와 프로젝트 자동 테스트, 테스트 작성과 실제 실행을 구분한다.
6. 지표가 있다면 실제 앱 결과와 예시 코드의 측정을 구분한다. 입력·측정 코드/명령·원시 결과·비교 조건을 연결한다. 필수 조건을 먼저 확인하고 측정하지 않은 지표는 미측정으로 둔다. 무작위·성능 실험은 필요한 경우 반복·난수·환경을 기록한다.
7. 현재 UC와 상위 기능의 상태를 각각 갱신한다. 사용자 행동·상태·성공/실패 흐름이 바뀌면 해당 기능의 ASCII 그림과 필요한 UC 상세도 갱신한다. 중요한 결정은 DECISIONS, 실행 방법 변경은 앱 README에 반영한다. 긴 로그는 링크로 연결한다. 결과·검증 범위·남은 작업을 짧게 보고한다.

타입 검사·컴파일·동작 검증은 필요한 범위에서 수행한다. 같은 조건의 유효한 기존 근거는 재사용한다. lint·포맷 검사와 자동 포맷은 사용자 요청이 있을 때만 실행한다. 실패를 숨기거나 미검증 상태를 완료로 표시하지 않는다.
